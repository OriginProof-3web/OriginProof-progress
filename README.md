## 1. 멘토링 요청사항

### 1.1 한 줄 요약

1~2회차 피드백을 반영해 **"카드 결제 알림 진위 확인"**에서 **"기관이 직접 발행한 공식 안내의 출처·원본 일치·현재 상태 검증 + AI 피싱 위험 설명"**으로 범위를 바꿨습니다.

- 송금·결제 흐름은 뺐습니다.
- 블록체인 역할은 **여러 독립 기관이 공동으로 관리하는 발행 권한·이력**으로 좁혔습니다.
- 기관 등록은 **2-of-3 공동승인**으로 합니다.
- 공식 안내는 **기관 지갑(EIP-712)으로 서명**하도록 개발 계획을 5.1로 개정했습니다.

### 1.2 1회차(김태경 교수) 피드백과 반영 내용

| 피드백 | 반영 내용 | 상태 |
| --- | --- | --- |
| 블록체인이 왜 필요한지 범위를 좁혀 설득하라. 은행이 굳이 우리 걸 쓸 이유가 있나? | "위변조 방지 때문에 블록체인이 필요하다"는 주장은 버렸습니다. 대신 **서로 독립적인 기관들이 발행 권한과 상태 변경 이력을 공유하고, 운영자 바깥에서도 같은 기록·규칙을 확인해야 한다**는 요구로 근거를 좁혔습니다. 중앙 서비스 하나만 운영할 때는 DB·투명성 로그 같은 대안이 더 단순하다는 점도 기획서에 적었습니다(수정본 4.1~4.4). | 기획 반영 |
| 블록체인에 무엇을 저장할지 확립하고, 중앙 DB와 하이브리드로 나눠라 | 온체인에는 기관 ID·발행 주소·키 이력·정지 이력, 문서 ID·소유 기관·버전·해시·유효기간·철회/대체 상태, 공동승인 기록, nonce만 둡니다. 원문·개인정보·AI 결과·사용자 입력은 PostgreSQL에 둡니다(수정본 4.2~4.3·7.1). | 기획 반영 · 구현 PR 리뷰 중 |
| 오라클 문제를 해결할 수 있는가? 데이터 업데이트도 체인에서 | "이 기관이 실제로 존재하고 발행 권한이 있는가"를 핵심 오라클 문제로 정의했습니다. 외부 명부 대조 → 도메인·업무 이메일 확인 → 담당자 권한 확인 → 키 보유 증명 → **독립 승인자 3명 중 2명 승인**으로 위험을 줄입니다. 내용 수정은 덮어쓰기 없이 **새 버전 발행 + 이전 버전 대체**를 한 트랜잭션에서 처리합니다(수정본 5장·8.3). | 기획 반영 · 구현 PR 리뷰 중 |
| AI 피싱 탐지는 블록체인과 별개에서 추가 검증처럼 제공하라 | AI는 "이 메시지가 무엇을 요구하고 무엇을 조심해야 하는가"만 답합니다. 공식 발행 여부는 서명·온체인 기록으로 판정하며 AI 결과와 섞지 않습니다. 발행 기록이 없는 메시지도 AI 분석을 받을 수 있습니다(수정본 6장). | 기획 반영 |
| 송금·결제는 빼고, 은행·기관이 등록하도록 유도하라 | 카드 결제 알림 MVP를 **기관 공식 안내(납부 안내·공식 문서 템플릿 2종)**로 전환했습니다. 기관은 공식 안내를 직접 발행·수정·철회해서 사칭·변조에 대응하는 주체로 참여합니다. | 기획 반영 |
| 개인 등록은 신뢰하기 어렵다. 기업 단위 이상으로 | 발행 주체는 심사·공동승인을 거친 **기관(기업 이상)**만 허용합니다. 일반 사용자는 조회·AI 분석만 합니다. | 기획 반영 |
| 정보취약자 지원, 보고서 형태 결과 제공 | 결과를 **공식 발행 / 원본 일치 / 현재 상태 / AI 위험**의 네 축으로 나눠 보여줍니다. 쉬운 문구와 큰 글씨를 쓰고, 색 하나로 "안전"을 선언하지 않습니다. "피싱 확률 87%" 같은 근거 없는 숫자는 쓰지 않습니다(수정본 6.4·9.3). | 기획 반영 · 화면 구현 중 |

### 1.3 2회차(김태경 교수) 피드백과 반영 내용

| 피드백 | 반영 내용 | 상태 |
| --- | --- | --- |
| 개인 지갑(메타마스크 등 핫 월렛)으로 인증·권한 부여 | 기관 담당자와 승인자 3명이 **각자의 EVM 지갑**으로 서명합니다. 서버는 기관 개인키를 수집·보관하지 않습니다. 지갑 소유 확인과 실제 신원·역할 확인은 분리합니다. 일반 사용자는 접근성을 위해 지갑 없이 조회할 수 있게 했습니다(ADR 0004). | 기획 반영 · 구현 PR 리뷰 중 |
| 입력 유형(텍스트·QR·녹음·링크)에 따라 산출물 형태를 다르게 | 입력별 결과 구조를 설계했습니다. 텍스트는 의심 문장, 녹음은 시간대, 문서는 페이지로 근거 위치를 표시합니다. QR만 스캔한 경우에는 "공식 기록 확인, 받은 내용은 미비교"로 구분해 보여줍니다. MVP에 넣을 입력 범위는 팀 회의에서 최종 확정합니다. | 입력 범위 확정 중 |
| 링크: 웹페이지·설치 파일이 진짜인지 체인 정보와 비교 | URL은 구조 분석과 공식 도메인 비교부터 시작합니다. 설치 파일 해시를 비교하는 기능은 후속 확장으로 정리했습니다. | 후속 |
| 검증을 지원하는 기관 목록을 노출 | 등록 기관 공개 조회 API(`GET /api/issuers/{id}`)와 화면에 참여 기관 목록을 표시할 계획입니다. | 계획 |
| LLM 앞단에 빠른 결정 모델을 두어 UX 개선 | 규칙 검사(키워드·패턴·도메인)를 먼저 실행해 즉시 결과를 보여주고, LLM 구조화 분석은 비동기로 덧붙입니다. LLM이 실패해도 규칙 검사 결과는 항상 제공합니다. | 구현 PR 리뷰 중 |
| 녹음 음성 분석의 활용 가능성과 한계 | STT 기반 대화 분석을 보조 기능으로 검토합니다. AI만으로 발신자 신원이나 사기 여부를 확정하지 않는다고 기획서에 적었습니다. | 검토 |

### 1.4 3회차 요청사항 (임명환 원장님께)

원래 멘토링 계획에서 3회차 주제는 "AI 분석 정량 검증"이었습니다. 원장님 전문 분야(토큰이코노미·RAG·AI-블록체인 융합)에 맞춰 아래 네 가지를 중심으로 자문을 요청드립니다.

1. **기관 참여 유인 설계(토큰이코노미)** — 기관이 비용과 책임을 지면서 참여할 이유를 어떻게 설계해야 할까요? 토큰 없는 허가형(permissioned) 구조와 토큰 인센티브 구조 중 어느 쪽이 공공·금융 기관 도입에 현실적인지 여쭙고 싶습니다.
2. **공동승인 거버넌스** — 2-of-3 독립 승인자는 실제로 어떤 주체(예: KISA, 금융보안원, 협회)가 맡는 게 타당할까요? 퍼블릭 테스트넷과 컨소시엄 체인 가운데 어느 쪽을 선택하는 게 맞을까요?
3. **RAG 기반 피싱 분석** — 공개 피싱 사례·수법 자료를 지식베이스로 두는 RAG 구조가 근거 제시와 환각 억제에 효과적일지 궁금합니다. 그 정확도를 어떻게 정량 평가할지도 여쭙고 싶습니다.
4. **AI·블록체인 융합의 설득력** — 본선 심사에서 "AI와 블록체인이 둘 다 꼭 필요하다"를 납득시키려면 어떤 지표와 시연을 보여줘야 할까요?

## 2. 최초 기획서 대비 변경된 기획서

최초: 본선 진출용 기획서(2026. 9. 8., OriginProof 10쪽) → 변경: 수정 기획서(1·2차 반영, 23쪽) + 통합 개발 계획서 5.1(2026. 10. 14.)

| 항목 | 최초 기획서 | 변경된 기획서 |
| --- | --- | --- |
| 검증 대상 | 참여 기관의 디지털 요청 (MVP: Origin Mock Bank 1곳, 카드 결제 알림 1종) | **기관이 발행한 공식 안내** (가상 기관 2곳, 납부 안내·공식 문서 템플릿 2종). 송금·결제 흐름 제외 |
| 핵심 질문 | "이 기관이 실제로 이 요청을 발행했는가?" | ① 발행 출처 ② 원본 일치 ③ 현재 유효 상태(철회·대체·만료·기관 정지) + ④ AI가 설명하는 피싱 위험 행동 |
| 블록체인 역할 | Issuer·Key 상태와 폐기만 온체인에 저장 | 기관 권한·키 이력·정지 이력 + **문서 소유·해시·버전·철회 상태** + 공동승인 기록·nonce |
| Web3 필요성 논리 | 서버가 신뢰 상태를 관리하면 단일 조작 지점이 됨 | 독립 기관들이 권한·이력을 공유하고 **운영자 밖에서도 검증**해야 함. 이 장점이 성립하는 조건 8가지와 한계(2명 공모, 같은 노트북 시연의 한계)를 명시 |
| 기관 등록 | 운영자(관리자)가 등록 승인 | 외부 명부·도메인·이메일·담당자 권한·키 보유 증명을 거친 뒤 **2-of-3 공동승인**. 긴급 정지는 1명 단독, 재활성화·키 교체는 2-of-3 |
| 발행 서명 | 서버 측 기관 서명(ECDSA secp256k1) | **기관 지갑의 EIP-712 서명**을 컨트랙트가 직접 검증. 중계자는 가스만 내고 내용을 바꿀 수 없음 |
| 내용 변경 | 철회 후 새 ID로 재발행 | 같은 documentId의 **다음 버전 발행 + 이전 버전 대체**를 한 트랜잭션에서 처리. 원본은 덮어쓰지 않음 |
| AI 역할 | 비정형 메시지의 필드 추출(Semantic Interface) | **피싱 위험 행동 분석·설명**: 규칙 검사 → LLM 구조화 출력 → 근거 문장을 실제 입력과 대조. 발행 판정과는 분리 |
| 결과 표현 | VERIFIED / UNVERIFIED / TAMPERED / INCONCLUSIVE / ERROR | 네 축 보고서(공식 발행·원본 일치·현재 상태·AI 위험) + AI 등급 HIGH / CAUTION / NO_CLEAR_SIGNAL / ABSTAIN. 확률 수치 미사용 |
| 사용자 입력 | 문자·스크린샷 | 텍스트·QR·원본 파일 우선. 이미지 OCR·녹음 STT·링크는 단계적 확장(입력 범위는 회의 후 확정) |
| 대상 사용자 | 사용자·기관·관리자 | 일반 사용자·**정보취약자**·발행 기관·공동 승인자·외부 검증자 |
| 보장 범위 | — | "보장하지 않는 것"을 명시: 내용의 사실성, 납부 의무, 행동 안전, 미등록 = 사기 아님 |
| 구현 전략 | 7주 일정(W1~W7) | P0/P1/P2 등급과 **축소 순서**를 미리 정해 시연 완결성을 우선함 |

### 2.1 그대로 유지한 것

- 슬로건 "Don't detect the fake. Verify the real.": 가짜를 탐지하기보다 진짜를 증명하는 접근
- 원문·개인정보는 체인 밖(PostgreSQL)에 두고, 체인에는 검증에 필요한 최소 정보만 저장
- 최종 판정은 AI가 아니라 결정론적 검증 엔진이 내림. 미등록을 피싱으로 단정하지 않음
- 기존 MVP의 인증·Operation 복구·화면·테스트 자산을 재사용하고, 전체 재작성은 하지 않음

### 로컬 실행

```bash
cp .env.example .env
UV_PROJECT_ENVIRONMENT=.uv-venv uv sync --all-packages --all-groups --locked
pnpm install --frozen-lockfile
make demo        # 웹 http://127.0.0.1:3000 · API 문서 http://127.0.0.1:8000/docs
make demo-stop
```

`make demo`는 정상 알림은 VERIFIED, 금액을 바꾼 알림은 TAMPERED로 판정되는 흐름을 한 번에 재현합니다.
